# 0.6 Breaking Migration

Version 0.6 upgrades Auth to Security 4, makes managed browser mutation
boundaries explicit, and removes provider objects from public facades.

## 1. Upgrade Security and configure the CSRF secret

Upgrade `@goobits/security` to 4.x with Auth. Every non-`off` managed CSRF mode
now requires one shared secret containing at least 32 UTF-8 bytes:

```ts
const auth = new GoobitsAuth({
	// ...
	security: {
		csrf: { secret: env.AUTH_CSRF_SECRET },
		rateLimit: { store: sharedRateLimitStore },
		audit: { emitter: auditEmitter }
	}
})
```

Use the same secret on every instance and rotate it as deployment-managed
credential material. Tokens are HMAC-signed and bound to the validated Auth
session. Anonymous requests use Security's protected host binding cookie.

## 2. Move outer origin validation out of the CSRF block

The removed managed configuration:

```ts
security: {
	csrf: {
		mode: 'off',
		validateExternalSecurityBoundary: verifyOrigin
	}
}
```

becomes:

```ts
security: {
	requestOrigin: {
		mode: 'required',
		validate: verifyOrigin
	},
	csrf: { mode: 'off' }
}
```

Most applications should omit `requestOrigin` and use Auth's default verifier,
which delegates to `@goobits/security/request-origin` and trusts the current
request URL origin plus `requestOrigin.allowedOrigins`. It rejects unsafe
browser requests with cross-site Fetch Metadata, a mismatched `Origin` or
`Referer`, or no browser origin context.

The `secure` profile may explicitly disable token CSRF while request-origin
verification remains required. The `strict` profile requires both. Apple's
OAuth `form_post` callback is intentionally exempt because its single-use state
and nonce own that cross-site callback boundary.

The standalone credential-handler option named
`validateExternalSecurityBoundary` is unchanged: it acknowledges a broader
application-owned wrapper that supplies both CSRF and rate-limit protection.

## 3. Stop reading provider instances from Auth

`OAuthProvider.config` no longer exists, and `auth.providers` no longer returns
live provider instances. It returns a frozen record of safe metadata:

```ts
auth.providers.google // { name: 'google', callbackMode: 'query' }
auth.providers.apple  // { name: 'apple', callbackMode: 'form_post' }
```

Keep any application-owned provider references at their construction site when
you need to call provider-specific public methods. Custom `OAuthProvider`
subclasses must store credentials in ECMAScript `#private` fields. TypeScript
`private` fields are ordinary enumerable runtime properties and are not an
adequate serialization boundary.

Custom provider constructors must also stop forwarding configuration to the
base class:

```ts
// Before
super('example', config)

// After
super('example')
```

Every provider now exposes a concrete read-only `callbackMode`; subclasses only
need to override it when they receive callbacks through `form_post`.

## 4. Apple JWKS behavior

No application configuration changes are required. Apple keys now use a
single-flight cache, refresh only after the verifier reports an unknown key ID,
cool down repeated unknown-key refreshes, back off failed fetches, and retain a
stale verified key set during bounded provider outages. A known-key invalid
signature never triggers a refresh.

## Verification

After migration, exercise a normal same-origin mutation, session rotation,
anonymous sign-in, Google and Apple callbacks, provider linking/unlinking,
passkey registration/login, and production startup validation. Confirm that
unsafe requests without a valid origin boundary fail before their managed Auth
handler runs.
